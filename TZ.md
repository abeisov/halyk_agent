# ЧАСТЬ I. ЗАДАЧА

## 1.1 Что требуется

Агент читает пакет PDF-документов и реестр транзакций, и по каждой паре **«сценарий × пункт договора»** заполняет три поля:

| Поле | Содержание | Допустимые значения |
|---|---|---|
| `status` | вердикт | `"COMPLIANT"` или `"BREACH"`, строго заглавными |
| `actual` | фактическое значение показателя, который ограничивает ковенант | положительное число, 2 знака после запятой |
| `evidence_txn_id` | транзакция, определяющая результат | ID или `null` |

**Масштаб публичного датасета:** 12 сценариев × 3 ковенанта = **36 ячеек**.

## 1.2 Состав датасета

```
data/public/
├── CASE.ru.md                 ← описание задачи от организаторов, читать первым
├── CASE.kz.md                 ← та же задача на казахском
├── documents/                 ← PDF с именами-хэшами (04eee2e9ba8c.pdf)
├── master_ledger_2025.csv     ← единый реестр всех заёмщиков
├── submission_template.json   ← каркас ответа, заполняем ячейки
└── ground_truth.json          ← ПРАВИЛЬНЫЕ ОТВЕТЫ
```

**`ground_truth.json` — главный инструмент разработки.** Он даёт измеримую метрику вместо догадок. В приватном датасете 9 августа его не будет.

**Особенности реестра:**
- один файл на всех заёмщиков
- **колонки категории нет** — классификация операций только по назначению платежа и контрагенту
- **несколько валют**
- расходы отрицательные, поступления положительные

## 1.3 Формат сдачи

```json
{
  "team": "...", "contact_email": "...", "model": "...",
  "answers": {
    "P1": {
      "6.1": {"status": "COMPLIANT", "actual": 1850000.00, "evidence_txn_id": null},
      "6.2": {"status": "BREACH",    "actual": 5400000.00, "evidence_txn_id": "TXN-P1-0020"},
      "6.3": {"status": "BREACH",    "actual": 300000.00,  "evidence_txn_id": "TXN-P1-0007"}
    }
  }
}
```

**Жёсткие правила:**
- Ключи **не переименовывать, не добавлять, не удалять**
- Список сценариев **читать из шаблона**, не хардкодить. В публичном — P1–P10, B1, B4 (B2 и B3 отсутствуют). В приватном набор будет иным
- `actual` — **всегда положительное**, включая расходы: берём модуль. Деньги — **в USD**. Коэффициенты — просто число (`1.68`, не `"1.68x"`)
- Заполнены обязательно: `team`, `contact_email`, `model`
- Пустая ячейка оценивается как неверная. **Заполнять все 36**

## 1.4 Оценка

| Поле | Балл | Механика |
|---|---|---|
| `status` | **0.50** | точное совпадение; **ошибка → вся ячейка = 0** |
| `actual` | **0.30** | `0.30 × max(0, 1 − e/0.05)`, где `e = \|ваше − ключ\| / \|ключ\|` |
| `evidence_txn_id` | **0.20** | точный ID; при `null` в ключе убывает по той же шкале вместе с `actual` |

Ячейки взвешиваются по сложности в итоговом зачёте.

**Три следствия для кода:**

1. **Вердикт — король.** Неверный `status` обнуляет ячейку целиком, каким бы точным ни было число. Основные силы на вердикт.
2. **На ratio-ячейках точное число стоит 0.50, а не 0.30.** Там, где в ключе `evidence = null`, эти 0.20 не даются автоматом — они убывают вместе с `actual`. Угадывать транзакцию в таких ячейках бессмысленно; удваивается цена точности числа.
3. **Ровно два знака после запятой.** Округление до тысяч убивает баллы: ошибка 2.5% забирает половину, 5% — всё.

# ЧАСТЬ II. ТРИ СЛОЖНОСТИ ДАТАСЕТА

## 2.1 PDF с именами-хэшами

Файлы называются `04eee2e9ba8c.pdf` — ни заёмщика, ни типа документа. Принадлежность определяется только по содержимому.

**Связка детерминированная, LLM не нужен:**

```
txn_id = "TXN-P1-0039"   →  scenario_id = "P1"        (регулярка по реестру)
account_id = "ACC-7801"  →  ровно один scenario_id    (словарь из реестра)
PDF содержит "ACC-7801"  →  документ относится к P1   (регулярка по тексту)
```

Каждый `account_id` соответствует ровно одному `scenario_id`. LLM подключается только как фолбэк: если `account_id` в тексте не найден — ищем по названию компании.

## 2.2 Мультивалютность

В реестре несколько валют, `actual` требуется **в USD**. Курсы искать в документах датасета.

Самая дорогая ошибка: посчитаешь в валюте операции — промахнёшься в разы и потеряешь и 0.30, и связанные 0.20. Конвертация делается **до любых агрегаций**, отдельной колонкой `amount_usd` в нормализаторе.

## 2.3 Классификация без категорий

Колонки категории в реестре нет. Что считать расходом на категорию X, кто связанная сторона, целевое ли использование — определяется по назначению платежа и контрагенту.

**Единственное место, где LLM реально незаменим.**

# ЧАСТЬ III. ГЛАВНАЯ ЛОВУШКА

Из `CASE.ru.md`: часть ковенантов **допускает превышение лимита при выполнении оговорки**, или **применяется только при срабатывании условия**. `actual` при этом — всё равно фактическое значение показателя, и оно **может быть выше лимита при статусе COMPLIANT**.

Значит наивное правило `actual > threshold → BREACH` даст неверный вердикт на части ячеек. А неверный вердикт обнуляет ячейку целиком.

**Вывод:** LLM должен извлекать из текста пункта не только метрику и порог, но и **carve-outs** (условия, при которых превышение допустимо) и **триггеры применимости** (когда ковенант вообще действует). Это ядро задачи, а не деталь.

# ЧАСТЬ IV. УЛИКА — КОНТРФАКТИЧЕСКОЕ ОПРЕДЕЛЕНИЕ

`evidence_txn_id` — **единственная транзакция, чьё удаление, переклассификация или корректировка меняет вердикт.** Убери её — вердикт становится другим.

**Не является уликой** транзакция, просто вносящая вклад в сумму: ни самая крупная строка в проверяемой категории, ни последняя перед закрытием периода, ни та, что случайно перевалила накопленный итог за порог. Это прямо оговорено.

Реализуется **кодом, не моделью**:

```python
def find_evidence(df, spec) -> str | None:
    base = evaluate(df, spec)
    if base.verdict == "COMPLIANT":
        return None
    candidates = [
        txn_id for txn_id in _relevant(df, spec)
        if evaluate(df.drop(index=txn_id), spec).verdict != base.verdict
    ]
    return candidates[0] if len(candidates) == 1 else None
```

Для коэффициентных и агрегатных проверок — `null`.

# ЧАСТЬ V. АРХИТЕКТУРА

## 5.1 Принцип

> **LLM понимает текст. Код считает числа.**

Ни одно число в `submission.json` не приходит из ответа модели. Модель не суммирует сотни строк — она выдаёт правдоподобное число. `txn_id` синтезирует в правильном формате, но такой строки в данных нет.

```
LLM:  текст пункта → метрика, порог, период, скоуп, carve-outs, триггер
код:  pandas → actual → сравнение → status → контрфактическая улика
```

## 5.2 Чего в проекте НЕТ и почему

| Технология | Почему не нужна |
|---|---|
| Qdrant / pgvector / Chroma | десятки PDF помещаются в контекст напрямую |
| Docker | нет векторной БД — нет сервиса |
| LlamaIndex, чанкинг, sentence-window | нечего индексировать |
| Реранкер, BM25, гибридный поиск | нет retrieval-слоя |
| LangGraph | 36 ячеек — обычный цикл |
| Streamlit | не сдаётся, на оценку не влияет |

При таком масштабе вопросы rate limits, параллелизма и времени прогона снимаются: 36 вызовов укладываются в бесплатный тир за минуты. Приоритет полностью на точность, а не на пропускную способность.

## 5.3 Пайплайн


# ЧАСТЬ VII. МОДЕЛИ ДАННЫХ

```python
# src/core/models.py
from pydantic import BaseModel, Field
from decimal import Decimal
from datetime import date
from typing import Literal, Optional

class Transaction(BaseModel):
    txn_id: str                    # как в исходнике
    scenario_id: str               # извлечён из txn_id
    account_id: str
    date: date
    amount: Decimal                # НЕ float, знак сохраняется
    currency: str
    amount_usd: Decimal            # после конвертации
    counterparty: str
    description: str

class SourceDoc(BaseModel):
    doc_id: str                    # имя файла-хэша
    scenario_id: Optional[str]     # определяется атрибуцией
    account_id: Optional[str]
    company_name: Optional[str]
    doc_type: Optional[str]
    text: str
    pages: list[str]

class CovenantSpec(BaseModel):
    scenario_id: str
    clause: str                    # "6.1" | "6.2" | "6.3"
    metric_description: str        # что именно измеряем
    threshold: Decimal
    operator: Literal[">=", "<=", ">", "<"]
    period_start: Optional[date]
    period_end: Optional[date]
    currency: str = "USD"
    scope_keywords: list[str] = Field(default_factory=list)
    scope_counterparties: list[str] = Field(default_factory=list)
    carve_outs: list[str] = Field(default_factory=list)
    trigger_condition: Optional[str] = None
    is_ratio: bool = False         # ratio → evidence обычно null
    source_doc_id: str
    raw_text: str
    confidence: float = Field(ge=0, le=1)

class CellResult(BaseModel):
    scenario_id: str
    clause: str
    status: Literal["COMPLIANT", "BREACH"]
    actual: Decimal                # положительное, 2 знака
    evidence_txn_id: Optional[str]
    confidence: float = 0.0
    fallback_used: bool = False
```

# ЧАСТЬ VIII. МОДУЛИ

## 8.1 `score.py` — пишется ПЕРВЫМ

Сравнивает `submission.json` с `ground_truth.json` по формуле из части I.4. Выводит: общий балл, разбивку по ячейкам, отдельно точность `status`, средняя ошибка `actual`, попадания по `evidence`.

**Без него разработка идёт вслепую.** С ним появляется цикл «правка → замер → правка».

## 8.2 `registry/normalizer.py` + `fx.py`

Реестр → `DataFrame`. Извлечь `scenario_id` из `txn_id` регуляркой. Построить словарь `account_id → scenario_id`, проверить однозначность. Конвертировать все суммы в `amount_usd` **до** любых агрегаций.

Суммы — `Decimal`, не `float`.

## 8.3 `attribution.py`

Для каждого PDF: регулярка `ACC-\d+` по тексту → `scenario_id` через словарь. Фолбэк — поиск по названию компании, затем LLM.

Результат в `data/processed/doc_index.csv`. **Проверить покрытие: у всех ли сценариев есть документы.**

## 8.4 `covenant/compiler.py`

Вход: текст пункта 6.1/6.2/6.3 из договора конкретного заёмщика.
Выход: `CovenantSpec`.

**Строго structured output** через `response_format` с JSON-схемой из pydantic, `temperature=0`. Ответ валидируется; при ошибке — ретрай с текстом ошибки в промпте, затем следующая модель в цепочке.

Промпт обязан требовать: `carve_outs`, `trigger_condition`, `is_ratio`, `confidence`. Это то, на чём проваливается наивная реализация.

## 8.5 `engine/evaluator.py` + `evidence.py`

Чистый pandas, ноль LLM. Фильтрация по `scenario_id`, периоду, скоупу → агрегация → `actual` (модуль, 2 знака) → сравнение с порогом с учётом carve-outs и триггера → `status`.

Улика — контрфактически, по алгоритму из части IV.

## 8.6 `output/serializer.py` + `validate.py`

Сериализатор **читает `submission_template.json`** и заполняет существующие ячейки. Новых ключей не создаёт.

Валидатор проверяет:
- [ ] структура идентична шаблону: те же сценарии, те же пункты
- [ ] `status` строго `"COMPLIANT"` / `"BREACH"`
- [ ] `actual` — число, положительное, 2 знака
- [ ] нет `null` в `status` и `actual`
- [ ] каждый непустой `evidence_txn_id` существует в реестре
- [ ] `team`, `contact_email`, `model` заполнены

Запускается перед каждой отправкой.

## 8.7 `run.py`

```bash
python run.py --input data/public --output submission.json
```

Без интерактива. `try/except` вокруг **каждой ячейки**: исключение → дефолт, не падение прогона. Дефолт: `status` — частотный класс из `ground_truth`, `actual` — ближайшая осмысленная оценка, `evidence` — `null`.

Пустая ячейка = гарантированный ноль. Дефолт = шанс на 0.50.

Лог по каждой ячейке: выбранный документ, метрика, порог, carve-outs, число, вердикт.

## 9.3 LLM-клиент

```python
import litellm
from tenacity import retry, stop_after_attempt, wait_exponential

MODEL_CHAIN = [s.model_main, s.model_fallback]

@retry(stop=stop_after_attempt(s.max_retries),
       wait=wait_exponential(multiplier=2, min=2, max=60))
def _call(model, messages, response_format=None):
    r = litellm.completion(model=model, messages=messages,
                           timeout=s.llm_timeout, temperature=0,
                           response_format=response_format)
    return r.choices[0].message.content

def complete(messages, response_format=None):
    last = None
    for m in MODEL_CHAIN:
        try:
            return _call(m, messages, response_format)
        except Exception as e:
            last = e
    raise RuntimeError(f"Все провайдеры недоступны: {last}")
```

`temperature=0` обязательно: иначе два прогона дадут разные ответы и вы не поймёте, помогла правка или нет.

# ЧАСТЬ XII. ПРАВИЛА СОРЕВНОВАНИЯ

Запрещено получать ответы вручную, в том числе через готовые агенты вроде Claude Code или Codex. Ими можно пользоваться **только для разработки решения**; все ответы генерирует ваш собственный агент. Разрешены любые модели, OCR- и vision-движки, библиотеки. Нарушение — дисквалификация команды.

| Можно | Нельзя |
|---|---|
| Claude Code пишет код агента | Чат с моделью → ответ вручную в JSON |
| Отладка на публичных данных | Правка чисел в `submission.json` |
| Ваш агент ходит в API любых моделей | Прогон датасета через чат-интерфейсы |

**Операционное правило:** финальный `submission.json` создаётся только запуском `run.py`. Если файл открывался в редакторе — прогоняйте заново.

# ЧАСТЬ XIII. `CLAUDE.md`

```markdown
# Агент проверки кредитных ковенантов (Halyk AI Challenge)

Дедлайн: 9 августа 2026, 14:00. Читай ТЗ.md. Первоисточник — data/public/CASE.ru.md.

## Железные правила
1. Ни одно число в submission.json не приходит из ответа LLM.
   LLM компилирует пункт договора в CovenantSpec, pandas считает.
2. evidence_txn_id — только df.loc[idx, "txn_id"], никогда не строкой.
   Улика определяется контрфактически: её удаление меняет вердикт.
3. Суммы — Decimal. Никогда float. actual — положительный, 2 знака.
4. Все денежные величины конвертируются в USD ДО агрегаций.
5. Список сценариев читается из submission_template.json. Не хардкодить.
6. Ключи шаблона не переименовывать, не добавлять, не удалять.
7. status строго "COMPLIANT" / "BREACH". Ошибка обнуляет ячейку.
8. Каждая ячейка в try/except. Ячейки не остаются пустыми никогда.
9. Все LLM-вызовы — structured output через pydantic, temperature=0.
10. Секреты только в .env, читаются только в config.py.

## Не забывать
- Часть ковенантов допускает превышение лимита при carve-out.
  actual может быть выше порога при COMPLIANT. Наивное
  actual > threshold → BREACH неверно.
- Категорий в реестре нет: классификация по описанию и контрагенту.
- Имена PDF — хэши. Атрибуция через account_id → scenario_id.

## Приоритет
Робастность важнее точности. Пайплайн, отработавший криво но целиком,
обгонит точный, упавший на середине.
```
